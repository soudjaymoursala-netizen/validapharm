### TD-001 — Étendre le pattern serverless existant (Cloudflare Workers) plutôt qu'un backend "Modular Monolith"
- **Statut** : **ACTÉE (25/08/2026, décision explicite de l'utilisateur)** — résout CONFLICT-001. Version révisée et simplifiée par rapport à la première proposition (backend serveur générique), sur demande explicite de l'utilisateur de challenger la solution la plus simple ne compromettant pas l'objectif.
- **Context** : PWA 100% navigateur actuelle, contrainte réelle du poste professionnel (pas d'installation locale). La Target Architecture présuppose un backend (Modular Monolith, base relationnelle, recherche, workers asynchrones) pour porter Source Intelligence/Search/Integration Gateway.
- **Problem** : la première option envisagée (introduire un vrai backend serveur — base relationnelle + stockage objet + moteur de recherche) est plus lourde que ce que l'objectif exige réellement à l'échelle actuelle du projet (mono-utilisateur), et ouvre une nouvelle surface d'infrastructure à héberger/sécuriser/sauvegarder.
- **Decision** : ne pas construire de backend serveur "Modular Monolith". À la place, **étendre le pattern serverless déjà construit et validé** (relais Cloudflare Workers, URS-NF-044ter, déjà testé joignable depuis le poste professionnel de l'utilisateur — AR-R-64, clos) :
  - **OCR/Document Intelligence** : un second Worker sans état, relais vers une API cloud de vision/OCR (même pattern exact que le relais IA existant) — pas de pipeline serveur dédié.
  - **Recherche** : index plein texte calculé côté navigateur (IndexedDB) pour l'usage actuel ; si le volume l'impose un jour, les embeddings deviennent de simples fichiers JSON dans le dépôt Git (déjà source de vérité), comparés côté client — pas de base vectorielle serveur.
  - **Stockage des sources/preuves** : le dépôt Git dédié existant, pas un nouvel object storage.
  - **Traitement asynchrone** : Cloudflare Queues (même compte Cloudflare que le relais IA), suffisant à l'échelle mono-utilisateur actuelle — pas d'orchestrateur de jobs serveur.
- **Pros** : zéro serveur qui tourne en continu, zéro nouvelle base de données à héberger/sécuriser/sauvegarder, zéro nouvelle dépendance de compte (même Cloudflare, même GitHub déjà utilisés et validés), risque et coût minimaux.
- **Cons** : pas de moteur de requêtes relationnelles complexes multi-entités à grande échelle — accepté explicitement car aucun besoin réel ne le démontre aujourd'hui (cohérent avec le principe de la cible : "un service n'est extrait que si un besoin démontré existe").
- **Risk** : Faible — réutilise une brique déjà en production et déjà testée réseau.
- **Rejected Alternatives** : (a) rester 100% navigateur sans aucune extension serverless — rejeté, dégraderait trop l'ambition Document Intelligence/Search ; (b) backend serveur complet (Modular Monolith, base relationnelle, object storage dédié) — rejeté comme disproportionné à l'échelle actuelle du projet, réévaluable seulement si un besoin réel et démontré apparaît.
- **Impact** : Débloque les Phases 7-8 du `CONVERGENCE_PLAN.md` sans point d'arrêt.
- **Reversibility** : Élevée — une fonction serverless ponctuelle se remplace ou s'étend sans migration lourde ; si un vrai besoin de backend complet apparaît plus tard, rien de ce qui est construit ici ne devient un frein (le Git reste la source de vérité dans tous les cas).
- **Complément (25/08/2026, Phase 6, décision explicite de l'utilisateur)** : le Worker OCR est réellement construit (`workers/ocr-relay/`). Fournisseur retenu : **Azure AI Vision (Read API)** — meilleur niveau gratuit au moment de la décision (5000 transactions/mois contre 1000 chez Google Cloud Vision, vérifié par recherche le jour même), déjà approuvé par l'utilisateur au même titre que Google Cloud Vision. Architecture délibérément swappable (`FournisseurOcr` interface, un seul fichier à ajouter/changer pour basculer vers Google Cloud Vision). Déploiement réel (compte Cloudflare/Azure, secrets, test de joignabilité réseau équivalent à AR-R-64) **reste à faire par l'utilisateur** — non exécutable depuis cette session distante, voir `workers/ocr-relay/README.md`.

### TD-002 — Remplacer la grille ACFC codée en dur par un `MethodProfile` configurable
- **Statut** : **ACTÉE** (recommandation claire, aucun arbitrage réel — convergence de 3 sources indépendantes : repo, mémoire de session, Target Architecture).
- **Context** : `grilleCriticite.ts` code en dur 9 critères, viole une interdiction explicite du package (*"Ne pas hard-coder 6/7/9 questions ACFC"*).
- **Problem** : impossible d'accueillir un client réel avec ses propres questions (4 à 10 selon les entreprises réelles étudiées).
- **Options** : garder tel quel (rejeté) vs `MethodProfile` (questions mot pour mot, version, source, date d'effet, règle de décision configurable).
- **Pros/Cons** : `MethodProfile` demande une réécriture du module et de ses 11 tests, mais aucune autre partie du code n'en dépend (remplacement isolé, faible risque).
- **Risk** : Faible techniquement, élevé si non traité (violation documentée qui persiste).
- **Recommendation** : à implémenter en priorité, cf. `GAP.md`.
- **Rejected Alternatives** : garder la grille figée avec un simple "mode client" en paramètre — rejeté, ne résout pas le problème de fond (les questions elles-mêmes doivent être données, pas choisies parmi des jeux prédéfinis).
- **Impact** : Élevé et positif (débloque tout le futur module Assessment).
- **Reversibility** : Élevée — c'est un module isolé, changement sans effet de bord.

### TD-007 — Le moteur de raisonnement (Mission→Context→AI) s'orchestre côté navigateur, jamais un nouveau backend

- **Impact** : Structurant pour la Phase 15 — un seul nouveau module (`logique-metier/raisonnement/`), aucune nouvelle infrastructure d'hébergement.

### TD-010 — "Validation State" (état de validation vivant) : une vue calculée diagnostique, jamais un remplacement automatique de `qualification_status`
- **Statut** : **ACTÉE** (revue panel E1-E7, 26/08/2026, `REVUE_PANEL_VISION_VALIDATION_ENGINEERING.md` Point A, en réponse au document de vision "Validation Engineering Platform" de l'utilisateur).
- **Context** : la vision demande de savoir à tout moment "si un système est toujours dans un état validé et pourquoi", recalculé après un changement détecté (VALIDATED → CHANGE DETECTED → IMPACT ANALYSIS → REQUALIFICATION REQUIRED → ... → VALIDATED).
- **Problem** : `AssetNode.qualification_status` (Structure Système) est aujourd'hui un statut saisi manuellement. Le dériver *automatiquement* d'une analyse d'impact reviendrait à faire prendre une décision réglementaire par une simple logique déterministe sans confirmation humaine — même erreur déjà interdite pour `CriticalParameter → CPP` (invariant #8, principe fondateur n°1).
- **Recommendation** : "Validation State" est une **fonction de lecture pure/diagnostique** (candidat naturel : un nouvel outil du Reasoning Engine, Phase 15) qui répond "voici ce que je constate et pourquoi, avec citations vers le graphe" — jamais une écriture automatique de `qualification_status`. Le statut officiel reste un acte humain distinct, déjà tracé (même patron que `Confirmation`/`TestCandidate`).
- **Impact** : Oriente une future extension du Reasoning Engine (au-delà de Phase 15) — n'introduit aucune nouvelle entité stockée dans l'immédiat.
- **Reversibility** : Élevée — fonction de lecture pure, aucune migration de schéma engagée par cette décision elle-même.

### TD-011 — GxP-by-design (e-signature/RBAC) : limite assumée documentée, TD-001 non rouverte, aucun garde-fou de façade
- **Statut** : **ACTÉE** (revue panel E1-E7, 26/08/2026, `REVUE_PANEL_VISION_VALIDATION_ENGINEERING.md` Point B).

- **Impact** : Aucun changement de code — clarification documentaire pure, protège contre une fausse assurance de conformité.
- **Reversibility** : Sans objet (décision documentaire) — TD-001 reste rouvrable plus tard sur besoin réel démontré.

### TD-012 — Prochaine capacité du Reasoning Engine : analyse d'impact de changement ancrée sur `QualityEvent`, pas un mode générique fourre-tout
- **Statut** : **ACTÉE** (revue panel E1-E7, 26/08/2026, `REVUE_PANEL_VISION_VALIDATION_ENGINEERING.md` Point C).
- **Context** : la vision détaille deux capacités IA non couvertes par les 4 outils actuels de Phase 15 : (1) analyse de qualité d'exigences (ambiguës/non-testables/doublons) ; (2) analyse d'impact de changement (Change → Composant → Requirement → Risk → Test → Evidence → Impact Assessment).
- **Problem** : construire les deux d'un coup répéterait l'erreur déjà évitée en Phase 13 (construire plusieurs capacités non éprouvées simultanément). La première (qualité d'exigences) suppose un texte source non structuré — relève de Source Intelligence (Phase 8a), pas du Reasoning Engine actuel qui lit des données déjà structurées.
- **Recommendation** : la prochaine capacité concrète du Reasoning Engine est une analyse d'impact de changement, directement câblable sur `QualityEvent` (Change Control, Phase 5)/`Requirement`/`Test`/`Evidence` déjà construits — prolonge exactement le scénario "changement de recette" déjà testé en Phase 15. L'analyse de qualité d'URS reste au backlog, dépendante de Source Intelligence, non engagée.
- **Impact** : Oriente le prochain incrément du Reasoning Engine après la Phase 17 (Mission workspace).
- **Reversibility** : Élevée — purement additif (nouveaux outils de lecture), aucune structure existante modifiée.

### TD-013 — Architecture Technique (PLC/SCADA/Server) : relations typées entre `AssetNode` existants, jamais une nouvelle entité d'équipement parallèle
- **Statut** : **ACTÉE** (revue panel E1-E7 condensée, 27/08/2026, `PHASE_18_ARCHITECTURE_TECHNIQUE_SPEC.md` §4, en réponse au document "VALIDAPHARM MASTER PRODUCT VISION / NORTH STAR").
- **Context** : la vision demande de modéliser Equipment/System/Subsystem/PLC/HMI/SCADA/Server/Database/Network/Software/Application/Interface et de tracer les relations belongs_to/controlled_by/connected_to/hosted_on/used_by entre eux.
- **Problem** : construire une nouvelle famille d'entités parallèle à `AssetNode` pour porter PLC/SCADA/Server dupliquerait un modèle d'équipement déjà générique et configurable — `AssetHierarchySchema.levels[]` (Phase 4/16) accepte déjà des niveaux nommés librement par le client (`level_key: string`, jamais une énumération figée dans le code), donc un client peut déjà créer des nœuds "PLC"/"SCADA"/"Serveur" sans aucun changement de code. Le vrai manquant est plus étroit : aucune relation *typée et dirigée* n'existe entre deux `AssetNode` (`associated_nodes[]` est un graphe libre non typé, incapable de distinguer "contrôlé par" de "connecté à").

Aucune nouvelle entité de nœud. Aucune détection de cycle (cohérent avec la tolérance déjà documentée d'`associated_nodes[]`).
- **Impact** : Structurant pour la Phase 18 — un seul ajout de table Dexie (v24), extension du Reasoning Engine avec un nouvel outil de traversal, aucune structure existante modifiée.
- **Reversibility** : Élevée — purement additif, aucune table existante modifiée, type de relation extensible sans migration future.

### TD-014 — Ingestion Office native : `jszip`+`DOMParser` pour la lecture `.docx`, Excel bloqué faute de librairie saine
- **Statut** : **ACTÉE** (recherche documentée, 27/08/2026, `PHASE_19_INGESTION_OFFICE_SPEC.md` §2, en réponse au chantier P0 "ingestion Office native" du plan `VISION_NORTH_STAR_CONVERGENCE.md`).
- **Context** : la vision exige de lire une procédure/un template `.docx`/`.xlsx` fournis directement par l'utilisateur — aucune librairie de parsing Office n'existait dans `package.json` avant cette phase.
- **Problem** : `mammoth` (candidat initial pour `.docx`) distingue son code Node de son code navigateur via le champ `browser` de son `package.json`, non appliqué par la résolution de modules de Vitest (SSR/Node) — installé et testé avec un `.docx` réel, l'erreur observée (`Could not find file in options`) a confirmé que le code exécuté en test n'était pas celui exécuté par la PWA réelle, malgré plusieurs tentatives de forcer la résolution (alias, `resolve.conditions`, `deps.inline`). `xlsx`/SheetJS (registre npm) porte une vulnérabilité haute (prototype pollution + ReDoS) sans correctif disponible sur npm (`npm audit`) ; `exceljs` introduit une dépendance transitive (`uuid`) avec une vulnérabilité modérée et une chaîne de dépendances datée.
- **Recommendation** : `.docx` — extraction directe du texte depuis `word/document.xml` avec `jszip` (dézippage, déjà 0 vulnérabilité) + `DOMParser` (API native, isomorphe Node/navigateur par construction, aucune ambiguïté de résolution). Excel — **aucune librairie installée** dans ce lot ; `xlsx_natif` n'est pas ajouté à `MethodeExtraction` tant qu'aucune solution saine n'est vérifiée (jamais une valeur de type sans implémentation réelle derrière). `docxtemplater`+`pizzip` (MIT, cœur gratuit, confirmé compatible navigateur) est retenu pour la future génération de documents au format client (Template Intelligence) — non installé dans ce lot, décision documentée par anticipation pour éviter une re-recherche.
- **Impact** : Structurant pour la Phase 19 — nouvelle dépendance `jszip` (production), `connecteurs/office/DocxNatifAdapter.ts`. Aucune capacité Excel dans ce lot (limite assumée, pas un oubli).
- **Reversibility** : Élevée — `jszip`+`DOMParser` est un choix additif ; réévaluer `mammoth` ou une librairie Excel reste possible sans migration si un correctif/une solution vérifiée apparaît.

### TD-015 — Une SOP n'est pas toujours du texte seul : images incorporées extraites séparément, filigrane/scan dégradé jamais "corrigé" algorithmiquement
- **Statut** : **ACTÉE** (27/08/2026, en réponse à une observation explicite de l'utilisateur sur la Phase 19 : "les SOP ne sont pas forcément qu'en Word, des fois c'est du Word avec des schémas et photos ou diagramme [...] et des fois c'est des SOP avec ou sans filigrane").
- **Context** : `extraireTexteDocx` (Phase 19) ne lisait que le texte de `word/document.xml`, ignorant silencieusement tout schéma/photo incorporé dans le `.docx` — une perte d'information potentiellement critique pour une procédure réelle. Par ailleurs, une SOP peut être un scan (image) portant un filigrane ("COPIE CONTRÔLÉE"/"DRAFT"), qui peut dégrader la qualité de l'OCR.
- **Problem** : ignorer les images incorporées reviendrait à lire une SOP en tronquant son contenu réel sans le signaler. À l'inverse, prétendre détecter/corriger algorithmiquement un filigrane sans preuve technique réelle serait une fabrication de capacité — exactement ce que la discipline "ne jamais fabriquer" interdit.
- **Recommendation** : `extraireImagesDocx` (nouvelle fonction, `connecteurs/office/DocxNatifAdapter.ts`) extrait chaque fichier `word/media/*` d'un `.docx`, avec son type MIME quand il est raster (png/jpeg/gif/bmp/tiff) — un format non raster (EMF/WMF, schéma Visio collé) est retourné explicitement avec `contentType: null`, jamais silencieusement omis. Ces images sont destinées à être transmises à l'OCR existant (`OcrRelayAdapter`, Phase 6) par un futur appelant, produisant une `Extraction` distincte sur la même `SourceVersion` (le modèle Phase 8a admet déjà plusieurs `Extraction` par version). Pour le filigrane/scan dégradé : **aucune détection/correction automatique construite** — le filet de sécurité reste la validation humaine déjà non négociable de tout `KnowledgeItem` (`a_valider` à la création). Documenté comme limite assumée, pas comme un problème résolu.
- **Impact** : Étend `DocxNatifAdapter.ts` (Phase 19) sans modifier son contrat existant (`extraireTexteDocx` inchangé). Aucune nouvelle dépendance.
- **Reversibility** : Élevée — purement additif.

### TD-016 — Cerveau procédural : structuration humaine d'une SOP versionnée, aucune extraction automatique de structure dans ce lot
- **Statut** : **ACTÉE** (revue panel E1-E7 condensée, 27/08/2026, `PHASE_20_PROCEDURAL_KNOWLEDGE_SPEC.md` §2/§4).
- **Context** : la vision (§12-15) demande de transformer une SOP en connaissance procédurale exécutable (étapes, conditions, exceptions, responsabilités), et de la suivre "comme le ferait un ingénieur humain".
- **Problem** : construire une extraction automatique de structure (texte libre → étapes) sans protocole de suggestion IA + confirmation humaine conçu et éprouvé fabriquerait une capacité non vérifiée — contraire à la discipline "ne jamais fabriquer" déjà appliquée à `KnowledgeItem` (Phase 8a, `valeur_interpretee` toujours fournie par l'appelant, jamais générée).

### TD-018 — Extension du parseur déterministe : reconnaissance par mot-clé, sous-titre comme contexte, repli ligne-par-ligne — maximiser la couverture sans IA avant tout repli
- **Statut** : **ACTÉE** (revue condensée, 27/08/2026, `PHASE_21_PARSEUR_STRUCTURE_PROCEDURE_SPEC.md` §8).
- **Context** : l'utilisateur, face à la démonstration d'un troisième genre de SOP réelle non couvert (voir Problem), demande explicitement de "concevoir ou étendre tous les champs possibles de parseur sans l'IA avant de passer au repli IA" — pousser le chemin déterministe à son maximum réel avant d'envisager la couche IA.
- **Problem** : sur demande de l'utilisateur ("as-tu un parseur capable de couvrir tous les types de SOP ?"), un troisième document réel du corpus Drive a été testé (IMA "4915BRP"/"LA1028BRP", procédures Back-up/Restore PLC/PC pour Ferring) — résultat concret et vérifié : 0 section canonique reconnue, 0 étape proposée. Ce document a un plan réel ("1. INTRODUCTION / 2. PLC Procedures / 2.1 Pre-requisites / ...") mais aucun libellé ne correspond exactement au dictionnaire TD-017, et ses instructions sont une phrase par ligne, sans puce ni numéro.
- **Recommendation** : trois extensions déterministes, chacune directement motivée par ce document réel, aucune spéculative :
  1. **Repli par mot-clé** (`MOTS_CLES_SECTIONS`) : quand le titre complet ne correspond à aucune clé exacte du dictionnaire, un mot fort à l'intérieur suffit ("PLC Procedures"/"PC Procedures (for HMI ima xface)" contiennent "Procedures" → `procedure` ; "INTRODUCTION" seul → `objectif`). Toujours un motif explicite testé, jamais un mot deviné — moins spécifique que la correspondance exacte (essayée en priorité), jamais moins déterministe.
  2. **Sous-titre comme contexte** (`RE_SOUS_TITRE`, `EtapeProposee.contexteDetecte`) : une ligne "N.M Titre" ("2.1 Pre-requisites") n'est jamais une nouvelle section ni une étape, mais son texte est retenu et attaché comme contexte aux étapes qui suivent — sans quoi deux procédures distinctes dans la même section ("Back-Up" vs "Restore") produiraient une liste plate indifférenciée.
  3. **Repli ligne-par-ligne** (`collecterLignesSection`) : une section `'procedure'` sans aucune ligne à puce/numéro (cas réel confirmé) utilise désormais chaque ligne non vide comme étape candidate, plutôt que de renvoyer une liste vide sur un document dont la structure est réelle mais moins formatée. Les puces/numéros explicites restent utilisés en priorité quand ils existent (haute confiance) — le repli ne s'active que s'ils sont absents.
- **Impact** : `EtapeProposee` gagne `contexteDetecte: string | null` (jamais persisté — même statut que le reste de `PropositionStructureProcedure`). Aucun changement de schéma Dexie. Retesté sur les deux SOP déjà couvertes (Sanofi/Ferring, TD-017) sans régression, puis sur le document IMA — désormais 3 sections reconnues (`objectif`/`procedure`/`procedure`) et des étapes extraites avec contexte.
- **Limite qui subsiste, non close par cette extension** : le genre "instruction technique illustrée par tableaux d'étapes" (Markem-Imaje, TD-017) reste hors couverture — ces extensions répondent au genre "procédure numérotée sans plan qualité", pas à celui-là. Une couverture déterministe "de tous les types de SOP" reste, par construction, hors de portée d'un système de règles : c'est la limite de fond documentée en TD-017, confirmée plutôt que contredite par cette extension.
- **Reversibility** : Élevée — purement additif, aucune régression sur le comportement déjà couvert (revérifié par test).

### TD-033 — Archivage protégé de client/projet : verrou local par mot de passe, dérogation explicite et étroite à "jamais de mot de passe" (§5) et à TD-011

- **Statut** : **ACTÉE** (demande explicite de l'utilisateur, 31/08/2026 — « rajouter la possibilité de supprimer un projet ou un client... avec un mot de passe »).

Dérogation étroite et documentée au cadrage §5 — pas une réouverture de TD-001/TD-011 : aucun compte multi-utilisateur, aucun rôle, aucune session, un seul enregistrement local (`profilLocal`, même patron que `connexionGitHub`).

- **Recommendation** : `logique-metier/securite/verrouLocal.ts` — PBKDF2-SHA-256 (100 000 itérations, sel aléatoire, Web Crypto API), jamais un hachage simple ni un mot de passe en clair. `useProfilLocalStore`/`ProfilLocal.vue` — enregistrement unique par installation. `ModaleConfirmationArchivage.vue` — composant réutilisé par `GestionClients.vue` (client) et `FicheProjet.vue` (projet), double garde (nom + mot de passe), affiche une invite à configurer le profil plutôt qu'un archivage silencieusement bloqué si aucun profil n'existe. `archiverClient`/`archiverProjet` (+ `desarchiverClient`/`desarchiverProjet`) dans les stores existants — jamais de suppression `db.clients.delete`/`db.projects.delete`.
- **Impact** : schéma Dexie v28 (nouvelle table `profilLocal`, champs additifs non indexés sur `clients`/`projects` — enregistrements antérieurs traités `statut: 'actif'` par absence de valeur, même garantie que `workspace_id`/`readiness` lors de migrations précédentes). Vérifié dans un navigateur réel (Playwright) : tentative d'archivage sans profil local → invite claire, aucune écriture ; profil configuré ; mauvais nom → refusé ; mauvais mot de passe → refusé ; les deux corrects → client archivé, disparaît de la liste active, persiste après reload, réapparaît dans « Afficher les clients archivés », désarchivage fonctionnel ; même parcours vérifié côté projet (`FicheProjet.vue`, redirection vers le tableau de bord après archivage) — aucune erreur console sur l'ensemble du scénario. Un bug réel trouvé et corrigé pendant cette vérification : `ModaleConfirmationArchivage.vue` n'appelait jamais `profilLocalStore.charger()` — après une navigation complète (rechargement de page), l'état Pinia repart à zéro et la modale affichait à tort "aucun profil configuré" même quand un profil existait réellement en base ; corrigé en chargeant explicitement dans `onMounted` du composant plutôt que de compter sur l'écran appelant.

- **Reversibility** : Élevée — purement additif (nouvelle table, nouveaux champs non-breaking, aucune fonction existante modifiée au-delà de l'ajout de `statut` par défaut `'actif'`).

### TD-042 — Résolution partielle de TD-014 : lecteur XLSX minimal (`jszip`+`DOMParser`) pour l'import d'architecture hiérarchique

- **Statut** : **ACTÉE** (demande explicite de l'utilisateur, 03/09/2026, en discutant l'import d'architecture de site — §5 de son parcours utilisateur détaillé).
- **Context** : TD-014 (27/08/2026) avait bloqué toute ingestion Excel, faute de librairie saine (SheetJS/exceljs — vulnérabilités non corrigées dans leur surface complète : macros VBA, formules, objets OLE, liens externes). L'utilisateur redemande explicitement une solution plutôt qu'un contournement en dernier recours par un format texte.
- **Vérification faite avant de trancher** : `jszip` est déjà une dépendance du projet (TD-014, utilisée pour lire les `.docx`) — `npm audit` (03/09/2026) confirme **0 vulnérabilité** dessus, à date. Un `.xlsx` est structurellement un ZIP de XML, exactement comme un `.docx` déjà lu en sécurité via `jszip`+`DOMParser` natif (jamais une librairie Excel généraliste).
- **Décision** : construire un lecteur XLSX **minimal et dédié** (pas une librairie généraliste), scope volontairement étroit :
  - décompresse uniquement `xl/worksheets/sheetN.xml` et `xl/sharedStrings.xml` via `jszip` (déjà vetté) ;
  - parse via `DOMParser` natif — jamais d'`eval`, jamais d'interprétation de formule (`<f>`), jamais de macro VBA (`vbaProject.bin` jamais ouvert), jamais de lien externe suivi ;
  - extrait uniquement les valeurs texte/nombre des cellules, ligne par ligne.
  Ceci réduit la surface d'attaque au strict nécessaire, contrairement à une librairie Excel complète qui doit gérer tout le format.
- **Convention d'interprétation retenue pour l'architecture** : chaque colonne = un niveau de hiérarchie (mappé sur `AssetHierarchySchema.levels[]`, déjà configurable par client — pas de niveau figé dans le code), chaque ligne = un nœud, colonne optionnelle `parent`/`code` pour les liaisons explicites transverses (hors arbre).
- **Repli explicitement positionné, pas comme format d'import principal** : un format texte structuré (Markdown à titres imbriqués, ou CSV à colonnes de niveau) reste utile mais positionné comme format d'**édition manuelle et de relecture** du résultat importé — pas comme voie d'import principale, car un consultant dispose plus souvent d'un export CMMS/ERP tabulaire que d'une architecture déjà rédigée en Markdown.
- **Limite assumée** : ce lecteur ne gère qu'un sous-ensemble volontairement étroit du format XLSX (valeurs de cellules simples) — pas les feuilles multiples avec renvois croisés complexes, pas les cellules fusionnées avec mise en forme conditionnelle, pas les formules calculées (une formule est lue comme la dernière valeur mise en cache si présente, jamais recalculée). Une extension reste possible sans réouvrir la question de sécurité (même lecteur, même surface).
- **Reversibility** : Élevée — nouveau module additif, aucune fonction existante modifiée.

### TD-043 — Authentification multi-utilisateur : OAuth GitHub comme identité, partage `owner_id`/`shared_with` en convention UX

- **Statut** : **ACTÉE** (décision explicite de l'utilisateur, 03/09/2026, via `AskUserQuestion` — "Convention UX (recommandé pour démarrer)").
- **Context** : `CONFLICT-004` (ajouté aujourd'hui, voir `ARCHITECTURE_CONFLICTS.md`) documentait une tension ouverte entre le mono-utilisateur assumé (TD-011, cadrage §5) et la demande narrative de comptes/rôles multi-utilisateur. L'utilisateur clarifie que ce n'est pas une aspiration vague mais un vrai modèle commercial : vendre l'outil à une entreprise, chaque employé son compte, sections communes à l'organisation partagées, projets dans l'environnement de chaque utilisateur avec partage possible à une personne/un groupe, vision long terme "lecture pour tous, écriture pour le créateur + les partagés".
- **Problem** : construire un système de comptes/mots de passe maison violerait directement TD-011 ("RBAC/signature électronique de façade interdite" — un mot de passe vérifié uniquement côté navigateur, sans backend, ne peut offrir aucune sécurité réelle mais *ressemblerait* à une authentification réglementaire si présenté sans précaution, exactement le piège que TD-011 a nommé).
- **Décision** : authentifier via **OAuth GitHub** plutôt qu'un système de mot de passe maison — chaque utilisateur se connecte avec son propre compte GitHub réel (authentification réelle, 2FA possible côté GitHub, jamais une façade). L'entreprise cliente a un dépôt Git par organisation (déjà le modèle actuel) ; les employés y sont ajoutés comme collaborateurs GitHub — réutilisation du modèle RBAC déjà mûr de GitHub (lecture/écriture/admin, équipes) plutôt qu'en inventer un. Reste cohérent avec TD-001 (pas de nouveau backend applicatif complet) : le flux OAuth ne nécessite qu'un échange de jeton côté serverless léger (même pattern que le relais IA/OCR déjà construit), jamais un serveur de sessions.
- **Niveau d'application du partage projet, tranché explicitement par l'utilisateur** : **convention UX**, pas une frontière de sécurité réelle. `Section.owner_id`/`shared_with: Array<{user_id, access_level}>` (déjà modélisés depuis la Phase 0, jamais câblés faute d'identité réelle jusqu'ici) pilotent l'affichage des contrôles d'édition dans l'interface, mais l'accès Git sous-jacent reste au niveau du dépôt entier — comme un collaborateur GitHub classique. Un utilisateur techniquement averti avec accès au dépôt pourrait contourner cette convention ; ce n'est jamais présenté comme une garantie de sécurité, exactement la même discipline honnête que le verrou local (TD-033).
- **Option explicitement écartée pour l'instant** : un service intermédiaire qui vérifierait et appliquerait les droits avant chaque écriture (sécurité réelle) — rouvrirait `CONFLICT-001` (réintroduction d'un backend applicatif), non retenu par l'utilisateur à ce stade.
- **Impact prévu** : nouveau flux d'authentification OAuth GitHub (remplace/complète le jeton personnel actuel), résolution de l'identité (`user_id`) pour peupler réellement `owner_id`/`shared_with`, garde d'affichage dans les écrans de section/projet selon les droits résolus. Portée détaillée à spécifier (Phase 37).
- **Limite assumée, à documenter explicitement dans l'UI** (même discipline que `ProfilLocal.vue`) : le partage de projet est une convention d'organisation de l'espace de travail, pas un contrôle d'accès opposable.
- **Reversibility** : Moyenne — touche l'authentification, mais additif par rapport au jeton GitHub personnel déjà utilisé (OAuth peut coexister avec un jeton manuel pendant la transition).
- **Statut amendé, voir TD-044** : le mécanisme d'identité (OAuth GitHub individuel) a été remplacé avant implémentation — la décision de fond (convention UX, `owner_id`/`shared_with`) reste inchangée et est celle réellement construite.

### TD-044 — Amendement de TD-043 : identité multi-utilisateur via le profil local, pas OAuth GitHub individuel

(2) Le profil local est stocké par poste (IndexedDB), pas synchronisé — un utilisateur changeant de poste doit resaisir son profil (même email) pour que `owner_id`/`shared_with` continuent de le reconnaître. (3) Le câblage de la garde d'affichage se limite à `FicheProjet.vue` (niveau projet) dans ce lot — `Section.owner_id`/`shared_with` (niveau section, déjà modélisé) et les écrans d'édition de section individuels restent backlog, à traiter si un second cas réel le justifie (même discipline que TD-029/TD-032).
- **Reversibility** : Élevée — n'affecte que la résolution d'identité et l'affichage ; n'importe quel mécanisme d'identité future (OAuth GitHub inclus, si un jour souhaité pour les clients qui en disposent) peut se substituer à `identifiantUtilisateurCourant()` sans changer le modèle `owner_id`/`shared_with` ni `peutModifierProjet`.
